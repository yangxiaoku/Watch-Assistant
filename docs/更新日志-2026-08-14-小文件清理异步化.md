# 小文件清理改为异步操作 + 状态轮询

- **日期**：2026-08-13
- **分支**：`codex/publish-main`
- **提交**：`89f2f78`（`feat(cleanup): async small-file cleanup via strm operation queue`）
- **父提交**：`d7983a8`

## 背景

小文件清理（预览 + 确认后回收）的 apply 原先是长同步 POST：几十个文件逐文件重验证 + 删除（各带 0.3s 节流）需要 1-3 分钟，超过常见客户端超时。空目录清理已有 `strm_operations` 记录 + 请求内执行。本次把 apply 改成真异步：apply 立即返回操作 id，后台 asyncio task 执行删除，前端轮询操作状态直到 succeeded/failed。

## 改动内容

### 后端

- **`src/watch_assistant/models.py`**：`StrmOperationKind` 新增 `SMALL_FILE_CLEANUP = "small_file_cleanup"`。
- **`src/watch_assistant/schemas.py`**：
  - `StrmOperationResponse.kind` Literal 加入 `"small_file_cleanup"`。
  - `SmallFileCleanupApplyResponse` 从 `{deleted, failed, total}` 改为 `{operation_id, status: "running"}`。
- **`src/watch_assistant/api/library.py`**：
  - `apply_small_file_cleanup` 改为异步：校验（library/confirm）→ `StrmOperationService.create`（kind=SMALL_FILE_CLEANUP）→ `claim_start` 领取租约 → `asyncio.create_task` 启动后台 runner → 立即返回 `{operation_id, status: "running"}`。
  - 新增 `_start_small_file_cleanup_operation_heartbeat` 与 `_run_small_file_cleanup_operation`：后台 runner 内用心跳保活租约，调 `small_file_cleanup_service.apply(..., operation_delay_seconds=0.3)`，成功时 `operations.complete(retired=deleted, failed=failed)`，`SmallFileCleanupError` 时 `operations.fail(error.code)`，其他异常 `operations.fail("small_file_cleanup_failed")`，取消时 `operations.fail("small_file_cleanup_cancelled")`。完成后写 `library.small_file_cleanup.applied` 审计事件。
  - fire-and-forget task 持有强引用（`app.state.background_tasks` set + done callback discard），避免 asyncio 在 task 仍 pending 时回收。
  - 并发保护：已有 running 的同类操作时返回 `409 small_file_cleanup_in_progress`；有其他 mutating 操作（full/incremental/cleanup）运行时返回 `409 strm_library_operation_conflict`。
- **`src/watch_assistant/services/strm_operations.py`**：
  - `_MUTATING_KINDS` 加入 `SMALL_FILE_CLEANUP`（同一 library 只允许一个 mutating 操作运行）。
  - `reconcile_cleanup_applied` 的 kind 白名单加入 `SMALL_FILE_CLEANUP`，避免取消/只读核对误拒或误放。
- **`src/watch_assistant/services/strm_scope.py`**：`_MUTATING_KINDS` 加入 `SMALL_FILE_CLEANUP`（fencing 一致）。
- **`src/watch_assistant/api/strm.py`**：`resume_strm_operation` 的不可恢复操作集合加入 `SMALL_FILE_CLEANUP`（后台 runner 无 manifest workflow，不能走通用恢复）。
- **`src/watch_assistant/services/api_errors.py`**：新增错误码 `small_file_cleanup_in_progress` 描述。

### 前端

- **`frontend/src/types.ts`**：`StrmOperationResponse.kind` 联合类型加入 `"small_file_cleanup"`；`SmallFileCleanupApplyResponse` 改为 `{operation_id, status}`。
- **`frontend/src/views/LibraryWorkbenchView.vue`**：
  - `operationLabels` 加入 `small_file_cleanup: "小文件清理"`。
  - `applySmallFileCleanup` 改为：apply 返回 `{operation_id, status}` 后清空预览/选择，显示"小文件清理执行中"，用 `pollStrmOperation` 轮询操作（复用现有 500ms 轮询与 generation 机制）直到 succeeded/failed，基于 `operation.retired / operation.failed` 显示完成提示。
  - 新增 `smallFileCleanupOperationMessage`，并让 `operationStatusMessage` / `operationPollingTimeoutMessage` / `pollStrmOperation` 支持 `small_file_cleanup` action/kind。
  - `retryLatestOperation` 与"恢复执行"按钮把 `small_file_cleanup` 排除（与 cleanup 一致，不可恢复）。
  - **顺手修复**：`applySmallFileCleanup` 入口 guard 原先写的是 `!smallFileBusy.value`（应用永远不会执行），改为 `smallFileBusy.value`。
- **`frontend/src/errorCatalog.ts`**：注册 `small_file_cleanup_in_progress`（RETRYABLE_CODES / ACTION_BY_CODE / ADDITIONAL_CODES / CATALOG）。

## 顾虑

1. **后台 task 生命周期**：task 由 `asyncio.create_task` 创建并持有强引用，但服务器进程崩溃（kill -9）时操作会停留在 RUNNING 直到租约（默认 5 分钟）过期，由 `recover_incomplete` / `recover_stale` 终态化（timeout/recovered）。文件已在回收站，可恢复，无永久删除风险。
2. **并发互斥面收窄到 library 级**：`_MUTATING_KINDS` 加入 `SMALL_FILE_CLEANUP` 后，同一 library 上运行小文件清理时会阻止 full/incremental/cleanup 同时运行（反之亦然）。这是预期安全行为，但用户需等待清理完成才能开始 STRM 同步。
3. **失败反馈延迟**：快照过期等校验原先在 apply 同步返回（409/503），现在移到后台任务，前端需轮询到 failed 才看到 `snapshot_stale` 等错误。属异步化的固有代价，预览已做过一次快照校验，命中概率低。
4. **`strmOperationNextStep` 文案**：操作详情面板对 small_file_cleanup 失败仍显示"确认快照仍有效后再恢复执行"，而该类型不可恢复。文案略有误导，未改动 `statusCatalog.ts` 以避免扩大改动面，可在后续迭代精修。
5. **无需数据库迁移**：`StrmOperationKind` 使用 `native_enum=False`（字符串列），新增枚举值不触发迁移。
