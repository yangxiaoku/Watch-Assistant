# 115 资源目录本地缓存与惰性访问设计（2026-08-16）

作者：排查会话（依据 2026-08-16 生产实测）
状态：设计稿（待评审后实施）
关联缺陷：P0-1 推送失败（inventory 刷新风暴）、P0-4 订阅触发风控、调用量敏感

---

## 一、背景与问题

2026-08-16 生产实测确立的事实：

1. **115 对调用量极敏感**：批量/高频调用（约 30-165 次窗口内）触发 405 或「黑洞」（连接建立无响应），窗口 30-60 分钟；用户已明确要求**调用间隔固定 3s、宁慢勿风控**。
2. **当前每次推送都可能触发全树重扫**：推送守卫要求所有启用库有「完整 + 新鲜（900s）」快照；不新鲜时 `_refresh_inventory_before_push` 全树扫描（414 条 ≈ 430 次调用 × 3s ≈ 21 分钟），且批量失败任务会逐任务触发（已有 120s 冷却缓存缓解，但仍是全树粒度）。
3. **订阅 AUTO 批量推送**（单轮 30+ 任务）在快照新鲜窗口内秒级连发提交 → 写风控。
4. 已部署的缓解（8336e21 / fb573d6）：订阅限流去重、刷新失败冷却、写节流 10s、判型 deadline 240s、3s 读节流、proapi 快失败回退。**但这些仍是"全量刷新"路线上的减速，不是架构性降本**。

**目标**：平时（订阅检查、推送去重核对、库存查询）**不访问 115**，全部命中本地缓存；只有"需要的时候"才访问资源文件夹——按需分级：

| 动作 | 115 访问量 |
|---|---|
| 推送前库存核对（指纹未变） | **0 次** |
| 指纹核对（TTL 过期后） | 1 次 `fs_info`（无判型） |
| 目录局部刷新（指纹变化） | 仅变化目录的列表页 |
| 全量树扫描 | 仅整理执行/手动触发 |

---

## 二、核心机制：目录指纹（Directory Fingerprint）

### 2.1 指纹来源

115 `fs_info`（1 次调用，无需判型）返回：

```
count        → 直接子项数（列表 count）
utime        → 目录修改时间（unix 秒）
folder_count → 子文件夹数（辅助）
```

**指纹 = (count, utime)**。目录内容（增删改）必然改变 count 或 utime 之一；指纹未变 = 该目录在 115 侧无变化，本地快照可信。

### 2.2 新增表 `directory_fingerprints`

```sql
CREATE TABLE directory_fingerprints (
    library_id  TEXT NOT NULL,   -- 媒体库 id（main / org-source-xxx）
    directory_id TEXT NOT NULL,  -- 115 目录 id（根或任意子目录）
    child_count INTEGER NOT NULL,
    utime       TEXT,            -- fs_info utime（字符串，115 返回格式）
    folder_count INTEGER,
    verified_at TEXT NOT NULL,   -- 本地核对时间（UTC ISO）
    PRIMARY KEY (library_id, directory_id)
);
```

- **根目录指纹 = 库内容的哨兵**：核对根指纹即可判断"库是否变化"。
- 子目录指纹用于局部刷新（指纹变化的目录向下递归核对）。

### 2.3 指纹核对调用（最便宜的 115 访问）

`fs_info({"cid": <dir_id>})`——1 次调用、无判型、响应小。3s 节流下成本 ≈ 3s + 0.5s。**这是"需要的时候"访问的最小单位**。

## 三、惰性访问协议（分级判定）

### 3.1 推送前库存核对（守卫改造，核心）

`InventoryPushGuard.check()` 改为三级（从便宜到贵）：

```
L0 本地判定（0 次 115 调用）
    ├─ 指纹缓存存在且 verified_at 在 TTL 内（默认 3600s）
    │    且 entries 快照完整 → 直接本地去重判定
    │    （EXACT_DUPLICATE / MEDIA_DUPLICATE / VERSION_DUPLICATE / NOT_FOUND）
    └─ 不满足 → 进入 L1

L1 指纹核对（1 次 fs_info）
    ├─ 读根目录指纹 → 与缓存一致 → 更新 verified_at → 回 L0 本地判定
    └─ 不一致 → 进入 L2

L2 局部刷新（仅变化的目录）
    ├─ 对指纹变化的目录：读列表页（fs_files 50/页 + 判型）
    ├─ 更新 entries + 指纹；子目录递归核对（每层 1 次 fs_info）
    └─ 刷新后重做本地判定
```

**效果**：正常情况推送 = **0 次 115 调用**；最坏情况（TTL 过期 + 根变化）= 1 次指纹核对 + 变化目录局部刷新（远小于全树）。

### 3.2 推送前刷新 `_refresh_inventory_before_push` 改造

- 不再做"全库扫描"，改为 **L0/L1 流程**：先本地判定；只有 L2 需要时才扫描（且只扫变化目录）。
- 失败冷却缓存（120s）保留，作为 L2 失败后的兜底。

### 3.3 库扫描调度器改造（120min 巡检）

- 调度触发时只做 **L1 指纹核对**（每库 1 次 fs_info，2 个库 = 2 次调用 ≈ 6s）。
- 指纹未变 → 直接完成（entries 快照继续有效）。
- 指纹变化 → 才升级为全量树扫描（自动整理/手动触发的语义不变）。

### 3.4 整理执行（全量扫描的唯一高频场景）

- `run-now` / 自动整理调度：**计划生成前必须全量**（整理要对全部源文件生成计划）——保持不变，但先做根指纹核对：未变且上次快照可用 → **直接复用上次扫描快照生成计划**（0 次调用）；变化 → 全量。
- 全量扫描调用量（~430 次 × 3s ≈ 21 分钟）接受——这是"需要的时候"。

### 3.5 订阅路径

- 订阅检查（搜索）不打 115（现状正确）。
- AUTO 推送创建任务 → worker 处理 → 守卫 L0/L1（0-1 次调用）→ 提交。
- 单轮限流 5 + 内容去重（已部署）继续生效。

## 四、缓存一致性

| 场景 | 机制 |
|---|---|
| 系统内写入（推送/整理移动） | 写入成功后把相关目录指纹置为"脏"（删除/标记），下次 L1 自动核对 |
| 用户 115 侧手动变更 | 指纹（count/utime）变化 → L1 检出 → L2 局部刷新 |
| 指纹核对失败（风控/黑洞） | 保留旧指纹 + 旧快照，守卫按旧快照判定（fail-safe 方向：宁可放行去重判断保守，不可反复打 115）；`verified_at` 不更新 → 冷却后重试 |
| 快照不完整（历史遗留） | 不允许进入 L0（要求完整快照证据，复用 `validate_complete_scan_evidence`） |

**守卫语义不变**（fail-closed）：本地缓存证据不足时仍拒绝提交（`inventory_index_incomplete`），但拒绝不再消耗 115 调用（冷却缓存已覆盖）。

## 六、分期实施

- **P1（守卫 0 调用）**：新增指纹表 + 扫描写指纹 + 守卫 L0/L1（TTL 3600s）。推送/订阅从"可能全量刷新"变为"0-1 次调用"。改动集中在 guard + scan 落盘。
- **P2（局部刷新）**：L2 目录级增量刷新（变化目录递归）。把"指纹变化"场景的调用量从全树降到变化子树。
- **P3（整理复用快照）**：自动化计划生成前指纹预检；调度器改巡检。
- 每期独立验证：P1 后推送应稳定 0 次 115 访问（日志 `inventory.refresh.*` 事件消失）；P2 后库扫描调度只产生指纹核对事件。

## 七、验证与风控约束

- 每期上线后：真实推送 1 条（守卫应 0 次调用）、订阅检查 1 轮、整理预览 1 次，观察日志调用分布。
- 全程遵守 3s 调用间隔；验证期间低频（每步间隔 >1 分钟），不再做连续全树扫描测试。
- 风控窗口期不实施任何 115 实测，只做离线测试（fake transport）与代码评审。
