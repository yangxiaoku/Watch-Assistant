# 更新日志：2026-08-14 推送成功判定修复（通知真正反映推送结果）

## 背景

推送任务的通知此前大量显示为错误：任务停在 `uncertain`（`availability_observer_unavailable`）
或 `failed`（`inventory_index_incomplete`/`inventory_index_stale`），任务抽屉里全是红色错误。
这不是 UI 配色问题——是后端对“推送是否真正成功”的判定链路在真实 115 上一直是坏的。

## 真实 115 复验发现（2026-08-14 线上实测）

1. **云下载推送会创建同名目录**：磁力推送到目标目录后，115 创建“种子名”目录，文件在目录
   内部；`clouddownload` 任务返回的 `file_id` 即该目录 id，不是单个文件。
2. **目录列表记录对文件与目录完全同形**：`fs_files`/`fs_files_app` 的 show_dir=1 列表是
   被列目录的完整直接子项，但记录里 `fc` 恒为 0 或 "0"、没有 `fid`/`is_dir`；
   `fc`/`file_category` 语义随接口漂移（legacy 文件索引文件 fc=1、app 列表文件 fc="0"），
   完全不能作判据。此前 gateway 把 `fc=0` 当目录，导致所有文件被当成目录。
3. **可靠的类型判据是 `fs_info` 响应的 `count`**：目录的 `count`（子树文件数）>0，
   文件的 `count`=0；`folder_count` 对纯文件目录为 0、目录也可能有非零 `play_long`，
   单独都不可靠。（未完成同步的磁力目录 count=0，会被暂判为文件，索引更新后下次扫描修正。）
4. **show_dir=0 列表是递归全树文件**（含嵌套子目录文件），不能与目录列表合并。
5. **fs_info 详情不回显对象自身 ID**，但带 `paths` 父链（末端即直接父级）：文件/目录详情
   都以“父链末端落在授权目录内”为锚验证身份，并把父目录登记为已观察目录。
6. **file-style 列表记录的 `cid` 是直接父级 id**：判型必须优先用 `fid`，否则目录内文件
   会被误判为目录（父目录 count>0），树扫描产生 `directory_cycle`。
7. `fs_info_app` 对文件（fid）请求返回空列表、对目录返回 dict，且接口会风控 405：
   非 Mapping 响应与 405 都必须回退 legacy 详情。

## 修复内容

- `adapters/p115_library_gateway.py`：
  - 目录列表以 `fs_info` 的 `count`/`folder_count` 判型（fc 不再作为判据）；
  - 判型优先用 `fid`（file-style 记录的 cid 是父级 id）；
  - 详情类型冲突（count>0 被按文件请求等）失败关闭；文件/目录详情均以 paths 父链
    落在授权目录内为锚验证身份并登记父目录；`fs_info_app` 返回非 Mapping（空列表）
    时回退 legacy 详情。
- `adapters/p115.py`：
  - observer 接受“推送对象是磁力目录”的情形：文件详情类型冲突时回退目录详情，
    对象已落在目标目录（文件或目录皆可）即返回 AVAILABLE；
  - `_readonly_gateway_for` 同时按目录授权 file_id。
- 扫描（page_size=1 树扫描）恢复正常完成：主媒体库 48 项、自动整理源目录 30 项，
  均 `completed`，推送前置库存检查通过。

## 已知限制

- 115 对 /files、/info 接口存在风控（405/429），密集调用（如批量 reconcile）会触发；
  风控期间扫描会以 gateway_error 失败，由扫描调度自动重试（最多 5 次后需手动重扫）。
- 未完成同步的磁力目录（count=0）会被暂判为文件，索引更新后下次扫描修正；
  推送任务的可用性确认仍以对象真实落在目标目录为准（fail-closed）。
- 历史 `failed`（inventory_*）任务的 retry 在部分工作流状态上返回 409/500
  （工作流阶段校验），属既有行为，未在本轮改动范围内。
