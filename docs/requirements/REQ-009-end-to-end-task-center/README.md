# REQ-009：端到端任务中心

| 字段 | 内容 |
|---|---|
| 版本 | V1.0 |
| 状态 | 开发中 |
| 更新日期 | 2026-07-31 |
| 优先级 | P0 |
| 依赖 | 现有任务状态机、REQ-001、REQ-002、REQ-004 |

## 1. 一句话定义

用一个关联任务视图串联搜索、检测、推送、115 状态、整理和 STRM 更新，让用户能看到每个资源当前走到哪一步、为何停止以及如何恢复。

## 2. 背景与目标

当前推送抽屉只覆盖 115 提交状态。新增整理和 STRM 后，如果每个模块各有任务页，用户仍无法判断一部影片是否已经真正入库。

目标：

- 建立一个顶层 workflow，关联各模块子任务。
- 展示阶段状态、耗时、失败原因和下一步。
- 支持安全重试、取消和人工介入。
- 使用 correlation ID贯穿日志、CLI、通知和审计。

## 3. 非目标

- 不强行把所有模块塞入同一个数据库表。
- 不用前端轮询结果推断真实业务状态。
- 不允许任务中心绕过各模块重试规则。
- 不承诺 115 无法提供的下载百分比。

## 4. 功能范围

| 编号 | 功能 | 优先级 |
|---|---|---|
| FLOW-001 | 顶层 workflow 与 correlation ID | Must |
| FLOW-002 | 子任务关联和阶段时间线 | Must |
| FLOW-003 | 统一中文状态和错误 | Must |
| FLOW-004 | 安全重试、取消和恢复 | Must |
| FLOW-005 | 人工确认和阻塞事项 | Must |
| FLOW-006 | 筛选、搜索和历史 | Must |
| FLOW-007 | CLI 与通知关联 | Must |
| FLOW-008 | 任务统计和 SLA | Should |

## 5. 标准流程

```text
发现资源 -> 内容检测 -> 等待确认 -> 推送 115 -> 确认接受
        -> 等待文件可用 -> 自动整理 -> STRM 更新 -> 完成
```

阶段可以按能力跳过，但必须写明原因，例如“内容检测未启用”“STRM 未配置”。

## 6. 顶层状态

- 进行中
- 等待用户确认
- 等待外部服务
- 部分完成
- 已完成
- 已取消
- 已失败
- 结果待确认

顶层状态由服务端根据子任务计算，并保存状态依据。`uncertain` 优先级高于普通失败，不能被后续界面刷新覆盖。

## 7. 操作规则

- 重试只作用于失败阶段及其未完成下游，不重复已确认成功的远端操作。
- 取消停止未开始任务；已到达 115 的请求不能假装撤回。
- 人工确认必须保存操作者、计划版本和决定。
- 子任务使用自己的幂等键，顶层 workflow 保存关联关系。
- 服务重启后恢复进行中流程，并核对遗留运行态。
- 一个 workflow 允许多个资源候选，但只能有一个当前选中方案。

## 8. 界面要求

- 任务中心列表展示影片、当前阶段、状态、开始时间和最近更新。
- 详情展示纵向时间线、阶段耗时、中文日志摘要和关联 ID。
- 明确区分“115 已接受”“文件已可用”“整理完成”“STRM 已更新”。
- 对可处理状态显示重试、确认、重新选择资源或查看设置。
- 支持按状态、阶段、媒体、订阅、Agent 和时间筛选。

## 9. API 与日志

API 返回顶层 workflow 和分页子任务，不返回敏感链接。REQ-003 可通过 CLI 查询和等待同一 workflow。所有阶段遵循 REQ-004，并共享 correlation ID。

## 10. 验收标准

- 搜索到 STRM 更新的每个阶段都能在一个时间线查看。
- 阶段跳过有明确原因。
- 重试不会重复提交已接受的 115 任务。
- uncertain 状态必须人工或远端核对后才能继续。
- 服务重启后时间线和关联关系不丢失。
- CLI、通知和日志中的任务 ID可跳转到同一 workflow。
- 顶层完成只在所有必需阶段成功后出现。

## 11. 分期建议

1. correlation ID和现有推送任务聚合。
2. 检测、整理、STRM 子任务接入。
3. 时间线、筛选和安全操作。
4. CLI、通知和统计联动。

## 12. 待确认项与建议默认值

| 决策项 | 默认值 |
|---|---|
| 历史保留 | 180 天 |
| 默认列表 | 最近更新优先 |
| 终态失败重试 | 用户显式触发 |
| uncertain | 禁止自动继续 |

## 13. 当前实现证据（2026-07-29）

- 已实现 workflow 与检测/推送任务的默认关联；任务创建、复用和手动重试均保留 `workflow_id`。
- 推送子阶段在任务入队、worker 正常完成、失败、`needs_auth`、`uncertain`、不支持类型和服务重启恢复时由服务端事务同步，不依赖前端轮询推断。
- 详情页和任务抽屉展示关联 workflow ID；相关 API、worker recovery、workflow API 测试已覆盖。
- 本轮验证：后端关键回归 `607 passed, 3 skipped`，前端单测 `101 passed`，Ruff 和生产构建通过。
- 本轮补充 FLOW-006：工作流列表增加服务端 `subscription_id`、`stage`、`stage_status` 筛选，证据见 `evidence/2026-07-29-workflow-filtering.md`。
- 本轮补充 FLOW-004/FLOW-005：增加受保护的人工确认和 fail-closed 取消接口，证据见 `evidence/2026-07-29-workflow-approval-cancel.md`。
- 本轮补充 FLOW-007：`watchctl workflow approve|reject|cancel` 复用同一审批/取消 API，保留统一错误和审计关联。
- workflow 取消现在会取消尚未开始的阶段，即使另一个阶段正在运行；运行中或 `uncertain` 子任务保持原状态，不伪造远端撤回。
- 推送任务新增原子 `queued -> cancelled` 取消接口和 `watchctl task cancel`，worker 已 claim 或远端结果可能已存在时 fail-closed 返回 `task_not_cancellable`。
- 本轮补充运行中整理操作的本地中止请求：排队操作立即取消，运行中操作持久化
  `cancel_requested` 并由 executor 在 transport 边界检查；远端写入尚未开始时最终为
  `cancelled`，写入已经开始时最终为 `uncertain`，不伪造远端撤回。
- 本轮补充 FLOW-002：整理 operation 可通过受保护 API 关联 workflow；排队、claim、成功、失败、
  不确定、取消和重试会同步 `organization` 阶段，关联使用持久 `workflow_id` 和 operation ID。
- 本轮补充 FLOW-002：资源搜索任务支持可选持久 `workflow_id`，在创建、恢复、运行和终态
  保存时同步 workflow 的 `discovery` 阶段；已有搜索任务关联其他 workflow 时返回稳定冲突，
  不覆盖原有关联。
- 本轮补充 FLOW-002：内容检测批次响应返回持久 `workflow_id`；缓存命中、worker 正常完成、
  部分结果和依赖失败都会在同一事务内同步 `inspection` 阶段及稳定原因码，服务重启后的批次
  仍沿用原关联。
- 本轮补充 FLOW-007：搜索和内容检测在子任务状态事务提交后发出带 workflow/correlation ID 的
  `workflow.stage_changed` 事件；仅可行动终态进入站内通知，运行中事件仍保留结构化日志但不打扰用户。
- 本轮补充 FLOW-007：推送任务创建、重试、取消、worker 终态和重启恢复也会在状态提交后发出
  同一阶段事件，通知和 CLI/日志可使用同一个 workflow ID 追踪 push 阶段。
- 本轮补充 FLOW-002：STRM 全量/增量/清理 API 支持可选 `workflow_id`，在开始、成功和失败时
  同步 `strm` 阶段；整理完成后的目录 dirty worker 会继承关联 workflow，并在成功、重试等待
  外部、最终失败和功能跳过时同步阶段状态。原有 STRM 开关、Scope、完整扫描和清理安全门禁
  保持不变。
- 本轮补充 FLOW-007：提交后的可行动 workflow 阶段事件（等待确认、等待外部、成功、跳过、失败、
  不确定、取消）会通过统一事件目录生成站内通知，复用通知偏好、30 分钟去重和 Webhook Outbox；
  普通启动/读取日志不会自动生成通知。
- 剩余阻断：真实 115 写入、STRM 真实播放契约及 PanSou/qB 外部网络基线仍按 `docs/requirements/BLOCKERS.md` 保持门禁关闭。
