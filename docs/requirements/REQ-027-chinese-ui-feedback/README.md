## 1. 一句话定义

建立全站统一的简体中文交互文案和结构化错误引导体系，让用户在成功、处理中、降级、失败、待确认和结果不确定时，都能明确知道“发生了什么、为什么、影响什么、下一步怎么做”。

## 2. 缺陷现状

当前问题不是个别按钮漏翻译，而是错误契约和交互反馈缺少统一设计：

- 后端大量返回 `tmdb_unavailable`、`settings_conflict`、`task_not_retryable` 等英文机器码。
- 部分接口会把内部异常字符串直接放入 `detail`。
- 前端通用 API 层把字符串 `detail` 直接作为 `ApiError.message`。
- 多个页面再把 `ApiError.message` 原样显示，导致英文码或技术异常直接暴露给用户。
- 任务详情可能直接展示后端 `error_message`，缺少中文原因和处理建议。
- 界面仍存在 `LAN workspace`、`PRIVATE WORKSPACE` 等非必要英文展示。
- “请求失败”“提交失败”“暂不可用”等提示没有说明影响范围、是否已生效、能否重试和去哪里处理。
- 加载、空数据、部分成功、配置缺失、权限不足、冲突和 uncertain 等状态缺少统一表达。

REQ-004 解决中文日志和审计，但不能替代全站表单、按钮、任务、通知和业务页面的即时反馈，因此需要独立需求。

## 3. 产品目标

- 所有面向普通用户的主文案使用简体中文。
- 机器错误码和用户文案分离，程序继续使用稳定英文代码。
- 每个可预期错误都有中文标题、原因、影响、建议动作和是否可重试。
- 写操作必须明确显示“未提交、处理中、已成功、部分成功、失败或结果待确认”。
- 用户可以从提示直接执行重试、刷新、重新登录、前往设置或查看任务等下一步。
- 表单校验定位到具体字段，不只显示页面顶部错误。
- 全站术语、状态、标点、时间、数量和操作动词保持一致。
- 新增功能必须登记用户可见状态和错误文案后才能验收。

## 4. 非目标

- 不把 TMDB、PanSou、qBittorrent、STRM、HDR 等产品名和行业术语强行翻译。
- 不删除机器错误码、请求 ID和技术诊断信息；它们作为辅助信息保留。
- 不向普通用户展示 Python 异常、HTTPX 错误、英文堆栈或第三方原始响应。
- V1 不建设完整多语言切换，简体中文为唯一主展示语言。
- 不用更长文案掩盖业务状态不明确的问题。
- 不在错误提示中泄漏 Cookie、Token、磁力、分享地址、完整路径或真实直链。

## 5. 用户场景

### 5.1 上游暂时不可用

错误码为 `tmdb_unavailable`。页面显示“影视信息暂时无法加载”，说明本次页面未更新，并提供“重新加载”；技术详情中可复制错误码和请求 ID。

### 5.2 设置并发冲突

用户保存设置时配置已被其他页面修改。系统显示“设置已在其他位置更新”，说明本次修改未保存，并提供“加载最新设置”，不使用笼统的“保存失败”。

### 5.3 115 登录失效

任务进入 `needs_auth`。系统说明“任务尚未提交到 115”，提供“前往 115 凭据设置”，重新认证后可以从原任务继续。

### 5.4 结果不确定

远端请求超时但可能已经接受。系统显示“暂时无法确认是否提交成功”，明确提示不要重复操作，并提供“查看任务状态”。

### 5.5 部分成功

批量检测 20 条资源，其中 16 条成功、4 条失败。提示显示完成数、失败数和影响，并提供“只重试失败项”，不把整个批次显示为失败。

## 7. 统一错误契约

API 错误响应建议统一为：

```json
{
  "error": {
    "code": "settings_conflict",
    "title_zh": "设置已在其他位置更新",
    "message_zh": "当前页面中的设置不是最新版本，本次修改尚未保存。",
    "suggestion_zh": "请加载最新设置，确认内容后重新提交。",
    "retryable": false,
    "action": "reload_settings",
    "field_errors": [],
    "request_id": "req_...",
    "correlation_id": "corr_..."
  }
}
```

规则：

- `code` 是稳定英文机器码，供 Web、CLI、MCP 和测试判断。
- 中文字段来自集中消息目录，不由路由临时拼接。
- `message_zh` 必须说明本次操作是否已经生效。
- `suggestion_zh` 只给出真实可执行的下一步。
- `retryable` 表示原操作在状态核对后是否适合重试。
- `action` 使用登记的动作枚举，不接受任意链接或命令。
- `field_errors` 用于字段级校验，包含字段 ID和中文说明。
- 所有错误返回请求 ID；普通用户可复制，但无需理解。

兼容过渡期间，前端可以按 `code` 使用本地消息目录；一旦服务端提供结构化显示字段，二者必须通过契约测试保持一致。

## 8. 中文消息目录

每个用户可见事件登记：

- 稳定 `code` 和版本。
- 使用场景、HTTP 状态和业务状态。
- 中文标题、详情模板和建议模板。
- 允许进入模板的安全参数。
- 是否可重试、默认动作和展示级别。
- Web、任务、通知、CLI 等适用终端。
- 对应日志事件码和帮助主题。

未登记错误：

- 开发和测试环境必须失败或显式告警。
- 生产环境显示统一安全兜底，不展示原始异常。
- 同时记录脱敏的 `ui.unknown_error_code`，推动补齐消息目录。

## 9. 文案结构与术语

### 9.1 错误和警告

统一结构：

```text
标题：发生了什么
说明：本次操作结果 + 原因 + 影响范围
建议：下一步操作
辅助：错误码、请求 ID、发生时间
```

禁止只显示：

- “Error”或“请求失败”。
- 裸露英文码，例如 `credential_validation_unavailable`。
- “未知错误，请联系管理员”作为所有兜底。
- 只有 HTTP 状态，没有业务含义。
- “稍后重试”但系统明确不可重试。

### 9.2 状态术语

全站统一使用：

| 机器状态 | 中文主文案 | 语义 |
|---|---|---|
| `queued` | 排队中 | 尚未开始执行 |
| `running/submitting` | 处理中/提交中 | 已开始但没有终态 |
| `completed` | 已完成 | 全部步骤成功 |
| `partial` | 部分完成 | 有成功项也有失败项 |
| `failed` | 处理失败 | 已确认没有完成 |
| `needs_auth` | 需要重新登录 | 凭据问题，需要用户操作 |
| `uncertain` | 结果待确认 | 可能已到达远端，禁止直接重提 |
| `cancelled` | 已取消 | 已确认停止后续处理 |
| `unsupported` | 当前不可用 | 当前版本或契约不支持 |

状态名称必须结合对象，例如“资源检测失败”“115 提交结果待确认”，不能只显示“失败”。

## 10. 反馈类型与使用规则

### 10.1 页面内状态

用于加载失败、空数据、能力未配置和需要持续处理的问题。必须保留在对应内容区域，并提供刷新、配置或返回入口。

### 10.2 临时成功反馈

保存设置、复制 ID、创建任务等确定成功操作可以使用短暂提示。提示应说明对象和结果，例如“质量策略已保存”，而不是“成功”。

### 10.3 对话框

只用于不可逆、高风险或需要明确选择的操作。对话框必须展示对象、数量、影响、是否可恢复和主要/次要操作，不使用浏览器原生模糊 `confirm` 文案。

### 10.4 任务型反馈

异步操作创建成功后显示任务 ID、当前阶段和“查看任务”。任务创建成功不等于业务处理成功。

### 10.5 通知

后台任务终态和离开页面后仍需知晓的结果进入 REQ-012；不为每次前台按钮点击重复发送通知。

## 11. 操作状态要求

每个写操作必须覆盖：

1. **操作前**：按钮名称明确对象和动作，禁用时说明原因。
2. **提交中**：按钮锁定并显示具体动作，例如“正在保存”。
3. **已受理**：异步任务显示“任务已创建”，不能显示“处理完成”。
4. **成功**：说明已改变的对象和数量。
5. **部分成功**：分别显示成功、失败、跳过数量和失败项入口。
6. **失败**：说明操作未生效或具体生效范围。
7. **uncertain**：禁止自动重提，提供状态核对入口。
8. **重试**：只重试安全失败项，保留原任务关联。

页面刷新或关闭后，异步任务反馈由 REQ-009 恢复，不能丢失为无状态提示。

## 12. 表单、配置与权限提示

- 必填、格式、范围和冲突错误显示在具体字段附近。
- 提交后自动聚焦第一个错误字段，并在页面顶部提供错误数量摘要。
- 输入前展示必要单位、范围和后果，不把关键规则放在失败后才说明。
- Secret 输入不回显原值，只显示“已配置、未配置、验证失败或已过期”。
- 权限不足时说明缺少的能力和可申请方式，不泄漏越权资源内容。
- 设置冲突必须提供“加载最新设置”，不能让用户盲目重复保存。
- 配置依赖缺失时提供跳转到对应设置分组的动作。

## 13. 空状态、禁用与降级

空状态必须区分：

- 尚未创建数据。
- 当前筛选没有结果。
- 搜索完成但没有找到资源。
- 上游失败，无法确认是否有数据。
- 权限范围内没有可见数据。
- 数据仍在加载或同步。

禁用按钮必须可以通过邻近说明、Tooltip 或详情解释原因。不得用相同“不可用”同时表示未配置、权限不足、版本不支持、远端故障和任务进行中。

降级页面应说明哪些功能仍可使用、哪些结果来自缓存以及数据更新时间。

## 14. 典型错误映射

| 错误码 | 中文标题 | 结果说明 | 建议动作 |
|---|---|---|---|
| `tmdb_unavailable` | 影视信息暂时无法加载 | 当前页面未更新 | 重新加载 |
| `rate_limited` | 请求过于频繁 | 本次请求未执行 | 等待后重试 |
| `settings_conflict` | 设置已在其他位置更新 | 本次修改未保存 | 加载最新设置 |
| `credential_rejected` | 凭据验证未通过 | 新凭据未生效 | 检查后重新验证 |
| `credential_validation_unavailable` | 暂时无法验证凭据 | 原配置保持不变 | 稍后重新验证 |
| `resource_snapshot_not_found` | 资源列表已更新 | 当前分页快照失效 | 返回第一页刷新 |
| `inspection_unsupported` | 当前环境无法检测资源 | 未创建检测任务 | 查看检测配置 |
| `task_not_retryable` | 当前任务不能直接重试 | 原任务状态未改变 | 查看任务详情 |
| `needs_auth` | 115 登录状态已失效 | 任务尚未继续提交 | 前往凭据设置 |
| `uncertain` | 暂时无法确认提交结果 | 可能已经到达 115 | 查看任务状态，勿重复提交 |

正式消息目录必须覆盖全部 API、任务、表单和能力错误，不限于上表。

## 15. 界面清理范围

必须盘点并处理：

- 页面标题、Eyebrow、按钮、菜单、筛选、占位符和 Tooltip。
- 加载、空状态、成功、警告、错误和禁用说明。
- 表单校验、保存反馈、确认对话框和权限提示。
- 任务状态、错误信息、重试和取消结果。
- 日志、通知、PWA Push、CLI 人工输出和 MCP 用户摘要。
- 后端框架默认 404、422、500 和认证错误。
- 时间、数字、文件大小、时区和量词格式。

品牌名和必要技术字段可保留英文，但必须有中文上下文，例如“STRM 同步失败”，而不是孤立的 `STRM ERROR`。

## 16. 无障碍与移动端要求

- 错误提示使用 `role="alert"`，进行中状态使用合适的 `role="status"`。
- 焦点在提交失败后移动到错误摘要或首个错误字段。
- 颜色不是唯一状态表达，必须同时有文字或图标标签。
- 屏幕阅读器可读出字段错误、任务状态变化和对话框标题。
- 移动端提示可换行，不遮挡主要按钮，不因长错误码导致横向溢出。
- 临时提示停留时间足以阅读；关键失败不得只用自动消失 Toast。

## 17. API、前端与测试治理

- 后端禁止把 `str(exception)` 作为用户消息返回。
- 前端禁止把未知 `ApiError.message` 或原始 `detail` 直接插入界面。
- 所有异常先转换为登记错误码和安全上下文。
- CI 对 Vue 模板和用户消息扫描未登记英文提示、裸状态枚举和原始错误输出。
- 消息目录执行参数完整性测试，缺失参数或未知参数必须失败。
- 每个 API 错误分支至少有契约测试；核心用户流程有界面断言。
- 截图测试覆盖桌面和移动端长中文错误、字段错误、部分成功和 uncertain。

允许英文的白名单应非常有限，包括品牌名、协议名、编码格式、机器错误码详情和用户输入内容。

## 18. 日志与诊断关联

- 用户提示和 REQ-004 日志共享稳定错误码、请求 ID和关联 ID。
- UI 文案与日志文案可以详略不同，但业务结论不能冲突。
- 用户复制诊断信息时只包含错误码、请求 ID、时间、应用版本和脱敏状态。
- 未知错误码、消息模板失败和英文泄漏记录独立质量指标。
- 普通用户界面不显示堆栈；管理员通过日志中心按请求 ID定位。

## 19. 验收标准

### 19.1 中文覆盖

- Web 和 PWA 所有主页面、弹窗、任务、设置和通知没有无白名单的英文主文案。
- 后端已知错误码不会作为用户主提示直接显示。
- Python 异常、HTTPX 错误、英文堆栈和第三方原始错误不会出现在用户界面。
- 状态枚举均通过统一中文目录展示。

### 19.2 指引质量

- 每个已知错误都说明本次操作是否生效、影响范围和下一步。
- 可重试错误提供安全重试；不可重试错误不显示无效重试按钮。
- `needs_auth`、冲突、权限不足和配置缺失可以直接跳转到对应处理位置。
- `uncertain` 明确禁止重复提交，并提供任务核对入口。
- 部分成功分别展示成功、失败和跳过数量。

### 19.3 表单和交互

- 字段错误定位到字段，提交后焦点移动正确。
- 异步任务受理与业务完成不会混淆。
- 禁用按钮和空状态均有明确原因。
- 360 CSS 像素宽度和系统字体放大下提示不溢出、不遮挡操作。

### 19.4 工程治理

- 所有 API 已知错误进入集中目录并通过契约测试。
- CI 能阻止新增裸英文用户文案和未登记错误码直接展示。
- 未知错误使用安全中文兜底，同时可通过请求 ID定位日志。
- 错误提示和日志经过敏感信息扫描，命中数为零。

## 20. 分期建议

1. 盘点全部用户可见文案、API 错误码、任务状态和英文泄漏点。
2. 冻结结构化错误契约、中文术语和消息目录。
3. 改造后端错误映射与前端通用 API 层，阻止原始错误直出。
4. 优先治理登录、搜索、检测、115 推送、任务和设置主流程。
5. 补齐空状态、表单、高风险确认、PWA、CLI 和新增需求。
6. 建立 CI 扫描、契约测试、截图验收和文案评审门禁。

## 21. 风险与依赖

| 风险 | 缓解措施 |
|---|---|
| 只翻译文字但状态仍不明确 | 强制结果、原因、影响和动作四要素 |
| 前后端消息目录漂移 | 共享契约、版本化和自动测试 |
| 中文模板泄漏敏感字段 | 参数白名单、统一脱敏和长度限制 |
| 大量历史错误遗漏 | 自动盘点、未知码指标和分批治理 |
| 提示过多打扰用户 | 区分页面状态、Toast、任务和通知使用场景 |
| 技术术语翻译不一致 | 集中术语表和文案评审 |

## 22. 待确认项与建议默认值
